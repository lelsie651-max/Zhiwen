# 织文平台边界说明

## 1. 通用底座能力

当前仓库已经形成可被多个产品线复用的中立底座，主要包括：

- Evidence-first 事实账本：`Fact` / `FactValue` / `Evidence` 及其不可变来源链。
- 一致性候选与人工决议账本：候选生成、人工 Decision 追加链、幂等与来源认证。
- Dynamic Schema 投影体系：原始 UFL 投影、审阅投影、知识视图投影。
- ProjectVersion 快照与认证：精确版本读取、Manifest/Hash 认证、fail-closed 边界。
- 平台中立只读查询层：`app/services/review_query.py`，供浏览器用户接口和外部适配器共同复用。

这些能力描述的是“如何安全地产生、认证、读取知识状态”，而不是某一条产品线的页面形态或外部平台接入方式。

## 2. 当前“一致性治理产品”专属能力

当前已经落地、并明确属于“一致性治理产品”的能力包括：

- HTML 工作台与项目页面。
- 用户态 Session 鉴权的 JSON API：当前用户、审阅列表、审阅详情、Decision 写入、Version Record 读取。
- 以“一致性候选 -> 人工判断 -> 认证后的当前状态回读”为中心的操作流。

这些能力依赖通用底座，但它们本身并不是通用底座的一部分，因为它们体现了当前产品的具体交互方式和运营边界。

## 3. 外部集成适配器

外部适配器目前只保留在集成边界上，不进入核心产品运行路径：

- Bailian 只读工具接口位于 `app/routers/bailian_tools.py` 与 `app/services/bailian_review_tools.py`。
- 其职责仅限于：Bearer 服务级鉴权、参数兼容、调用中立查询层、映射回既有 Bailian JSON 契约。
- 适配器可以被关闭；关闭后普通用户态前端、审阅、Decision、版本读取仍可独立运行。

因此，Bailian 是可替换的外部接入层，不是织文系统的业务地基。

## 4. 普通用户前端与外部 Agent 的边界

两类入口必须长期隔离：

- 普通用户前端：
  - 使用 Session 身份。
  - 必须校验 `project_members` 访问权。
  - 需要 CSRF 与受控 CORS。
- 外部 Agent / 插件：
  - 使用服务级 Bearer Token。
  - 不代表具体用户，不承载浏览器安全语义。
  - 只允许通过显式来源身份读取既有认证结果。

因此，浏览器接口不能复用外部共享 Token，外部 Agent 也不能被当作普通用户接口的替代入口。

## 5. 未来产品如何复用底座

未来若建设“书籍辅助阅读器”“规则管理”等产品，应优先复用以下内容：

- 事实账本与来源认证模型。
- Dynamic Schema 投影与版本快照认证。
- 中立查询层与 Decision 追加链。

而新的产品层应自行定义：

- 自己的页面与 API 入口。
- 自己的权限语义。
- 自己对事实、版本、规则的展示与交互方式。

换言之，应复用“认证过的数据能力”，而不是直接复用当前一致性治理产品的页面和路由。

## 6. 为什么不使用长期 Git 分支维护多个产品

长期分支会把同一套账本语义、投影算法和安全边界拆成多份演化历史，带来：

- 不变量漂移；
- 修复难以同步；
- 回归验证成本持续升高；
- 最终无法判断哪条分支才代表真实底座。

当前更合适的方式是在单仓库、单主线下维护共享底座，并用清晰的模块边界隔离产品层和外部适配器。

## 7. 何时才值得抽取独立私有 `zhiwen-core` package

只有在同时满足以下条件时，才值得把共享底座抽成独立私有包：

- 至少有两个独立产品线长期同时演进；
- 它们都稳定复用同一批底座能力；
- 底座 API 已经足够稳定，能承受版本发布与兼容承诺；
- 独立发布带来的收益，高于当前单仓库内联开发的协调成本。

在此之前，过早抽包只会把频繁变化的内部接口固化成额外维护负担。

## 8. 为什么当前阶段不做大规模目录重构

当前阶段的重点是先把边界做对，而不是追求目录外观：

- 现有代码仍在快速演进，目录大搬迁会放大回归面。
- 当前最紧迫的问题是“普通运行路径与外部适配器解耦”，这已经通过中立查询层与开关完成。
- 只要模块依赖方向清晰、测试能守住边界，目录是否一次性完全重排并不是最高优先级。

因此，当前选择的是最小必要重构：抽出中立查询层、保留既有兼容接口、增加开关与架构约束测试，而不是进行大规模文件迁移。
