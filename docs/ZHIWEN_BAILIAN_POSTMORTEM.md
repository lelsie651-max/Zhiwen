# 织文 × 百炼集成复盘

## 1. 结论先行

百炼集成在当前仓库中已经证明“可接入、可联调、可读取”的能力，但尚不足以被描述为稳定生产主链路。  
织文当前对百炼的定位应是：

- 已验证的外部只读集成
- 可替换
- 非核心业务地基

## 2. 已成功完成的三个只读工具

当前仓库里已经落地并经过测试/联调的 3 个工具为：

1. `bailianListReviewItems`
2. `bailianGetReviewItemDetail`
3. `bailianGetVersionRecord`

对应路由位于：

- `app/routers/bailian_tools.py`

底层 service 位于：

- `app/services/bailian_review_tools.py`

## 3. 当前代码中已确认的集成边界

- 鉴权方式：`Authorization: Bearer <BAILIAN_TOOL_TOKEN>`
- 安全方案名：`BailianToolBearer`
- 接口只读
- 输出带 `payload_hash` 与来源 manifest
- 工具侧不承担用户会话身份
- 浏览器用户接口与百炼工具接口已分层

## 4. 多工具插件被运行时重命名的问题

在实际联调中，曾观察到插件侧的工具展示名/运行时工具实例与配置期认知不完全一致，这会增加：

- tool name 映射歧义
- 观察日志与实际工具调用的对应成本

这不是织文业务算法的失败，而是外部运行时层的集成复杂度。

## 5. 拆分为单工具插件的解决方式

在联调实践里，把多工具插件拆成单工具插件，有助于：

- 减少工具选择歧义
- 降低工具名映射混乱
- 更快判断某次失败到底是鉴权、路径、参数还是运行时选择问题

这是一种联调稳定性优化，不改变织文后端的业务模型。

## 6. Tool ID 业务透传机制

联调中可以确认：

- Tool ID 与业务 UUID 可以沿插件配置和调用链透传
- 但工具真正是否被执行，仍取决于百炼运行时是否完成真实 HTTP 调用

换句话说，“thoughts 里出现了业务参数”不等于“织文后端已经收到请求”。

## 7. 真实功能调用结果

已经客观证明的功能包括：

- review items 可以返回待审事项列表
- review item detail 可以返回完整事实详情、候选值与证据
- version record 可以按精确 `project_version_id + subject_key` 返回记录
- Bearer 鉴权、公网访问、OpenAPI 暴露、payload hash 均已打通

## 8. 首轮调用 10 次仅 6 次真实执行

联调阶段观察到：百炼首轮调用并非每次都能稳定落到后端。  
按已有记录，10 次首轮中只有 6 次形成了真实执行。

这说明问题更多在外部运行时层，而不是织文本地的只读工具实现本身。

## 9. `tool_call` 被作为文本输出的问题

在部分场景中，模型会把“应该调用工具”的意图表达成文本，而不是触发真实工具执行。  
这会导致：

- 用户界面看起来像做了工具调用
- 实际日志里没有对应 HTTP 请求

因此任何百炼侧问题都必须结合：

- cloudflared / 网关日志
- FastAPI access log
- 织文端 HTTP 状态码

不能只看 Agent 文本结果。

## 10. T2 / T3 高延迟

联调中还观察到：

- 某些阶段的响应延迟明显升高
- 尤其是更深轮次或更复杂工具交互时，稳定性和时延都不理想

因此当前不建议把多轮 Agent 交互作为织文产品的核心体验入口。

## 11. 为什么百炼只保留为可替换集成

原因很直接：

1. 织文的核心可信状态来自本地账本、投影、manifest 与版本认证。
2. 百炼运行时存在工具命名、真实执行率、文本退化和延迟等外部不确定性。
3. 这些问题不应该反向侵入织文内部的数据模型和系统不变量。

所以合理定位是：

- 百炼是“可接可换”的读取层
- 不是系统事实链、决议链、版本链的根基

## 12. 不记录的敏感信息

本复盘明确不记录以下信息：

- API Key
- `BAILIAN_TOOL_TOKEN`
- 数据库密码
- 完整数据库 URL
- 完整 Authorization Header

未来继续补充本文件时，也必须保持相同边界。
